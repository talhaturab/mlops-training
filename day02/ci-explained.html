CI/CD, in plain English

How one git push replaces the six commands you typed yesterday.

01Every pipeline is four words

Yesterday you changed one line and then typed six commands: build the image, save it, upload it, load it, remove the old container, start the new one. Strip away the tools and you did four things: you tested (if you remembered), you built, you published, and you deployed. Every CI/CD system on earth is those four words with a machine doing the typing.

CI, continuous integration, is the first two: every change is tested and built the moment it lands, so problems surface in minutes, not on release day. CD, continuous delivery, is the last two: what passed is published and put where users can reach it, the same way every time.

02The pipeline, and where it stops

A pipeline is a list of jobs. Each job is a list of steps, each step a command. Jobs can depend on each other, so a failed job stops everything behind it. That dependency is the whole safety story: a red test means no image gets built and nothing reaches the server, and nobody had to remember to check.

Ours has three jobs. test runs on every push and every pull request. build-and-push waits for test and runs only on main. deploy waits for the build and runs only when the repository knows where the server is.

03What a runner actually is

Every job runs on a runner: a fresh virtual machine that GitHub starts for you, uses for a few minutes, and throws away. It has nothing on it that you did not put there in the steps. That is why the workflow installs uv and runs uv sync --frozen before testing: the lockfile from Day 1 is what makes the runner's environment match yours.

This is the strongest argument for the pipeline. "Works on my machine" cannot happen, because the machine is new every time and anyone can read the script that set it up.

For ML engineers: a runner is a clean training job. Same data (the repo), same recipe (the lockfile), same code; a different result would mean a real bug, not a stale environment.

04A registry instead of a file on a laptop

Yesterday the image lived in a .tar.gz on your disk and reached the server only because you carried it there. Today the build job pushes it to GitHub Container Registry, ghcr.io, and the server pulls it from there. Two things improve at once: the upload leaves your laptop, and pushes only send the layers the registry has not seen, so a code-only change moves a few megabytes, not 300.

The image gets two tags. oracle:<sha>, the first seven characters of the commit, is exact and never changes; the deploy job pulls that one. oracle:latest moves with every build and exists for humans. Deploying latest is one of yesterday's mistakes; the pipeline avoids it for you.

Logging in to the registry needs no password of yours. Every workflow run is issued a short-lived token, GITHUB_TOKEN, with exactly the permissions the job declares. Ours declares packages: write, nothing more.

05Where things live now

The pipeline needs three things to reach your server: the address, the user name, and the SSH key. The first two are variables, visible to anyone who can read the repo settings. The key is a secret: write-only, masked in logs, never readable again through the interface. Your laptop no longer needs to keep any of them.

06The workflow file, the parts that matter

The full file is .github/workflows/oracle.yml. Read it top to bottom like the Dockerfile. These are the lines to understand; the rest is plumbing.

# what starts it
on:
  push:         { branches: [main], paths: ["day01/oracle/**"] }
  pull_request: { paths: ["day01/oracle/**"] }

# two pushes at once queue up instead of racing
concurrency: { group: oracle-pipeline, cancel-in-progress: false }

jobs:
  test:
    runs-on: ubuntu-latest              # a fresh VM
    steps:
      - uses: actions/checkout@v4       # get the code
      - uses: astral-sh/setup-uv@v6     # get uv
      - run: uv sync --frozen           # the lockfile, again
      - run: uv run ruff check . && uv run pytest -q

  build-and-push:
    needs: test                         # red test = no image
    if: github.ref == 'refs/heads/main'
    permissions: { packages: write }    # the built-in token may push
    steps:
      - uses: docker/build-push-action@v6
        with: { platforms: linux/amd64, push: true,
                tags: ghcr.io/OWNER/oracle:SHA, ghcr.io/OWNER/oracle:latest }

  deploy:
    needs: build-and-push
    if: vars.EC2_HOST != ''             # forks without a server stop here
    steps:
      - run: |                          # yesterday's commands, verbatim
          ssh -i key ec2-user@$EC2_HOST '
            docker pull ghcr.io/OWNER/oracle:SHA
            docker rm -f oracle
            docker run -d --restart unless-stopped -p 8000:8000 --env-file ~/.env \
                       --name oracle ghcr.io/OWNER/oracle:SHA'
  1. on

    Triggers. The paths filter means editing a README does not rebuild the image. Pull requests run tests only, so nothing is published from an unreviewed branch.

  2. needs

    Ordering. Jobs run in parallel unless told otherwise. needs draws the arrows from Figure 2.

  3. frozen

    Reproducibility. The runner installs exactly what your lockfile says, the same way the Dockerfile does. Three environments, one source of truth.

  4. SHA

    Exact deploys. The commit hash is the image tag. What is running on the server can always be traced to a line in git history.

  5. secrets

    Nothing typed. The registry login uses the run's own token; the SSH key comes from a secret. No credential ever appears in the file or the logs.

07Mistakes to make on purpose, once

  • Pushing without the paths filter and rebuilding a 300 MB image because a README changed.
  • Deploying :latest. Two runs finish out of order and the older image wins.
  • Pasting the SSH key into the YAML "just to test". It is now in git history forever.
  • Pulling a private package without logging in. The server's docker pull is refused; our deploy job logs in with the run's token first.
  • Letting deploy run on pull requests. Every stranger's branch would replace production.
  • Green pipeline, broken app: no health check after deploy. Ours curls /health from outside.

The one sentence to remember: a pipeline is yesterday's commands written down once, run by a machine that is new every time, and stopped by the first thing that fails.
