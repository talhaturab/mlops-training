00The words a workflow is made of

The file is YAML: indented keys and values, nothing more. GitHub Actions gives a handful of those keys meaning. Learn these and you can read any workflow, not just ours.

workflow
The whole file. One file, one pipeline. It lives in .github/workflows/ and GitHub picks it up automatically.
on
The events that start it: a push, a pull request, a schedule, a click.
job
A unit of work that gets its own fresh machine. Jobs run in parallel unless one needs another.
step
One thing a job does, in order. Either run a shell command or uses an action.
uses
Reuse a published action, someone else's tested step, pinned to a version like @v4.
run
A shell command, exactly as you would type it. Multi-line with |.
needs
Wait for another job, and only continue if it succeeded. This is how the chain is built.
if
A condition. The step or job is skipped, not failed, when it is false.
${{ … }}
An expression GitHub evaluates before running: contexts like github.ref, secrets.X, vars.X, needs.job.outputs.x.
secrets
Values you paste into the repo settings once and can never read back. Masked if they appear in logs.
vars
Like secrets but readable: addresses, user names, feature flags.
GITHUB_TOKEN
A token minted for each run, scoped by permissions, dead when the run ends.

01The header comment

1# The Oracle's pipeline. Read it top to bottom, like the Dockerfile.
2#
3#   push to main ──▶ test ──▶ build-and-push (image to GHCR) ──▶ deploy (SSH to EC2)
4#   pull request ──▶ test
5#
6# Every step here is one of the six commands from Day 1, done by a machine instead of you.
  1. 1–8

    A comment block. YAML ignores lines starting with #. This one is for the next person who opens the file: it draws the pipeline and states the one idea behind it. Every file that automates something should start by saying, in words, what it automates.

02What starts it

8name: oracle
9
10on:
11  push:
12    branches: [main]
13    paths: ["day01/oracle/**", ".github/workflows/oracle.yml"]
14  pull_request:
15    paths: ["day01/oracle/**", ".github/workflows/oracle.yml"]
  1. name

    The label GitHub shows in the Actions tab and in the status ticks next to commits. Purely cosmetic, but pick something you can find in a list.

  2. on

    The triggers. This section answers one question: which events on GitHub should start this pipeline? Two are listed.

  3. push

    Someone pushed commits to the main branch, and at least one changed file sits under day01/oracle/ or is this workflow itself. The paths filter is what stops a README edit from rebuilding a 700 MB image.

  4. pull_request

    Someone opened or updated a pull request touching the same paths. There is no branch filter here on purpose: every proposed change gets tested, but as you will see below, only main gets built and deployed.

03Queueing and shared names

17# Two people pushing at once: runs queue up in order instead of racing each other.
18concurrency:
19  group: oracle-pipeline
20  cancel-in-progress: false
21
22env:
23  APP_DIR: day01/oracle
24  IMAGE_NAME: oracle
  1. concurrency

    What happens when two runs overlap. All runs share one group name, so GitHub runs them one at a time, in order. cancel-in-progress: false means a new push waits for the current run rather than killing it. For a deploy pipeline that is the safe choice: you never want half of one deploy and half of another on the server.

  2. env

    Two values used in several places, defined once. APP_DIR is where the app lives inside the repo; IMAGE_NAME is the last part of the registry path. Change either here and every job follows.

04Job 1: lint and test

27  # ---------------------------------------------------------------- 1. test
28  test:
29    name: Lint and test
30    runs-on: ubuntu-latest
31    defaults:
32      run:
33        working-directory: ${{ env.APP_DIR }}
34    steps:
35      - name: Check out the code
36        uses: actions/checkout@v4
37
38      - name: Install uv
39        uses: astral-sh/setup-uv@v6
40        with:
41          enable-cache: true
42          cache-dependency-glob: "day01/oracle/uv.lock"
43
44      - name: Install locked dependencies
45        run: uv sync --frozen
46
47      - name: Lint
48        run: uv run ruff check . && uv run ruff format --check .
49
50      - name: Test
51        run: uv run pytest -q
  1. jobs

    The list of jobs. Each job gets its own fresh virtual machine. Unless told otherwise, jobs run at the same time, in parallel.

  2. runs-on

    Which machine. ubuntu-latest is a Linux VM that GitHub creates for this job and deletes afterwards. It has Docker, Python, git, and curl on it, and nothing of yours.

  3. defaults

    Every run command in this job starts inside day01/oracle, so the commands read exactly as they do on your laptop.

  4. checkout

    Get the code. A fresh VM has no idea what repo it is working for. This step clones the commit that triggered the run. It is the first step of almost every job ever written.

  5. setup-uv

    Install uv, the same tool you use locally, with a cache keyed on the lockfile so repeated runs skip the download when nothing changed.

  6. --frozen

    Install exactly what the lockfile says. No resolving, no "latest". This is the same line the Dockerfile runs. Laptop, image, and runner now agree byte for byte.

  7. Lint, Test

    The two commands from make lint and make test. If either exits non-zero, the step fails, the job fails, and because the next job needs this one, nothing else runs. Nobody has to remember to check.

05Job 2: build the image and push it

53  # ------------------------------------------------------ 2. build and push
54  build-and-push:
55    name: Build image and push to GHCR
56    needs: test
57    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
58    runs-on: ubuntu-latest
59    permissions:
60      contents: read
61      packages: write          # lets the built-in token push to ghcr.io
62    outputs:
63      image: ${{ steps.meta.outputs.image }}
64    steps:
65      - name: Check out the code
66        uses: actions/checkout@v4
67
68      - name: Work out the image name
69        id: meta
70        # ghcr.io requires a lowercase owner; GitHub usernames may not be.
71        run: |
72          owner=$(echo "${{ github.repository_owner }}" | tr '[:upper:]' '[:lower:]')
73          echo "image=ghcr.io/${owner}/${IMAGE_NAME}" >> "$GITHUB_OUTPUT"
74          echo "sha=${GITHUB_SHA::7}" >> "$GITHUB_OUTPUT"
75
76      - name: Log in to GitHub Container Registry
77        uses: docker/login-action@v3
78        with:
79          registry: ghcr.io
80          username: ${{ github.actor }}
81          password: ${{ secrets.GITHUB_TOKEN }}
82
83      - name: Set up Buildx
84        uses: docker/setup-buildx-action@v3
85
86      - name: Build for x86 and push
87        uses: docker/build-push-action@v6
88        with:
89          context: ${{ env.APP_DIR }}
90          platforms: linux/amd64
91          push: true
92          # Two tags: an exact one for machines, a moving one for humans.
93          tags: |
94            ${{ steps.meta.outputs.image }}:${{ steps.meta.outputs.sha }}
95            ${{ steps.meta.outputs.image }}:latest
96          cache-from: type=gha
97          cache-to: type=gha,mode=max
  1. needs

    Wait for test and require it to have passed. This single word is the safety story of the whole pipeline: no green tests, no image.

  2. if

    Only on a push to main. A pull request has already been tested above; it must not publish anything. The two conditions together mean: proposed changes are tested, accepted changes are shipped.

  3. permissions

    What the job's token may do. Every run is handed a short-lived token, GITHUB_TOKEN, that expires when the run ends. Here it is allowed to read the repo and write packages, which is exactly enough to push an image, and nothing else.

  4. outputs

    A value handed to the next job. Jobs run on separate machines and share nothing, so anything the deploy job needs, such as the image name, has to be declared as an output here.

  5. meta

    Work out the image name. The registry wants a lowercase owner and GitHub usernames need not be, so a tiny shell script lowercases it and writes two values into $GITHUB_OUTPUT, which is how a step publishes values for later steps.

  6. login

    Log in to ghcr.io using the run's own token as the password. No human password appears anywhere.

  7. buildx

    Enable the builder that can target another CPU architecture and use a remote cache.

  8. build-push

    Build for x86 and push. platforms: linux/amd64 matches the t2 instances. Two tags are written: the seven-character commit hash, which never moves, and latest, which always points at the newest build. The cache-from and cache-to lines store the image layers in GitHub's cache, so a code-only change rebuilds one layer, exactly as on your laptop.

06Job 3: deploy to the server

99  # --------------------------------------------------------------- 3. deploy
100  deploy:
101    name: Deploy to EC2
102    needs: build-and-push
103    runs-on: ubuntu-latest
104    # Only runs when the repo has the EC2_HOST variable set. Forks without it stop here.
105    if: ${{ vars.EC2_HOST != '' }}
106    environment:
107      name: ec2
108      url: http://${{ vars.EC2_HOST }}:8000
109    steps:
110      - name: Put the SSH key where ssh expects it
111        run: |
112          mkdir -p ~/.ssh
113          printf '%s\n' "${{ secrets.EC2_SSH_KEY }}" > ~/.ssh/deploy_key
114          chmod 600 ~/.ssh/deploy_key
115          ssh-keyscan -H "${{ vars.EC2_HOST }}" >> ~/.ssh/known_hosts 2>/dev/null
116
117      - name: Pull the exact image and swap the container
118        run: |
119          image="${{ needs.build-and-push.outputs.image }}:${GITHUB_SHA::7}"
120          cat > remote.sh <<'REMOTE'
121          set -euo pipefail
122          image="$1"
123          docker pull "$image"
124          docker rm -f oracle 2>/dev/null || true
125          docker run -d --restart unless-stopped -p 8000:8000 --env-file ~/.env --name oracle "$image"
126          for i in $(seq 1 30); do curl -sf localhost:8000/health >/dev/null && break; sleep 1; done
127          curl -s localhost:8000/health; echo
128          docker image prune -f >/dev/null
129          REMOTE
130          ssh -i ~/.ssh/deploy_key "${{ vars.EC2_USER || 'ec2-user' }}@${{ vars.EC2_HOST }}" bash -s "$image" < remote.sh
131
132      - name: Smoke test from the outside
133        run: curl -sf "http://${{ vars.EC2_HOST }}:8000/health"
  1. needs

    Wait for the image to exist. Same word, same rule: nothing gets deployed that was not just built from tested code.

  2. if

    Only when the repository knows a server. vars.EC2_HOST is a repository variable set in the GitHub settings. A fork that has not set it stops cleanly after the build instead of failing with a confusing SSH error.

  3. environment

    A named target with a link. GitHub shows deployments per environment and turns the URL into a clickable "View deployment" button on the run. Later this is where you add approval gates for production.

  4. SSH key

    Put the private key where ssh looks for it. The key comes from the secret EC2_SSH_KEY, which is write-only in GitHub and masked in logs. chmod 600 is the same permissions rule from Day 1. ssh-keyscan records the server's fingerprint so ssh does not stop to ask "are you sure?".

  5. remote.sh

    Yesterday's commands, written down. The script is created on the runner and then piped into ssh with bash -s, which runs it on the server. Inside it: pull the exact image by commit hash, remove the old container, start the new one with the same flags you typed by hand, wait until /health answers, and prune old images so the disk does not fill up. set -euo pipefail makes the script stop at the first error instead of carrying on blindly.

  6. --env-file

    The OpenRouter key is still ~/.env on the server. The pipeline does not touch it; it only restarts the container that reads it. Day 4 moves that file into a secret manager.

  7. smoke

    Check from the outside. The container saying it is healthy on localhost is not the same as a user reaching it. This last curl goes through the public IP and the security group, the way a browser would. If it fails, the run is red even though everything "worked".

07How to read any workflow you meet

  • Start at on. What starts this? Until you know that, nothing else makes sense.
  • List the jobs and draw the needs arrows. That is the pipeline diagram; everything else is detail.
  • Find every if. These are the places where the pipeline deliberately does nothing. They are usually the most important lines.
  • Find every secrets. and vars.. That is the list of things the pipeline needs from outside the repo, and therefore the list of things a new team member has to set up.
  • Read the run blocks last. They are the commands you already know, written down once.

The one sentence to remember: a workflow is a list of jobs, a job is a list of steps, and the arrows between jobs are spelled needs.
