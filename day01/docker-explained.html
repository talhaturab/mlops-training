Docker, in plain English

How we get the Oracle off your laptop and onto a machine you have never touched.

01The problem we are solving

The Oracle runs on your laptop because your laptop has everything it needs: Python 3.12, about forty packages at exact versions, two model files, a .env file, and a free port 8000. A rented cloud machine has none of that. You could install it all by hand, but you would do it again on every machine and after every change, and one day you would miss a step, load a different scikit-learn, and get different answers. "Works on my machine" is the default state of software.

Docker fixes this by letting you describe the whole environment in a text file, build it once into a single package, and run that identical package anywhere.

02What a container actually is

A container is an ordinary process on a Linux machine that has been given its own private view of the filesystem, its own network, and its own process list. From the inside it looks like a small dedicated computer. From the outside it is just a process, which is why it starts in a second and twenty fit on one box.

It is not a virtual machine. A VM boots a whole operating system with its own kernel; a container borrows the host's kernel and only carries the files on top. Think shipping container: a standard box any crane, truck, or ship can move without caring what is inside.

For ML engineers: an image is to a container what a trained model artifact is to a running inference process. Build the artifact once, store it, start as many live copies as you need. Same file in, same behaviour out.

02.1Image versus container

Say it out loud: the image is the frozen thing you build and ship; the container is the live thing you run. If a container misbehaves, delete it and start another from the same image. Nothing you do inside a running container changes the image.

03The six words you need

Dockerfile
A recipe. A short text file listing the steps to assemble the environment, top to bottom.
image
The result of running the recipe. A frozen, read-only snapshot of a filesystem with your app inside. It never changes once built.
container
A running copy of an image. Start it, stop it, throw it away; the image is untouched. Run many from one image.
layer
Each line in the Dockerfile adds one layer to the image. Unchanged layers are cached, so rebuilds only redo what changed.
registry
A place to push images so other machines can pull them. Docker Hub, GitHub Container Registry, every cloud has one. Git for images.
tag
A label on an image, like oracle:day2. Use something meaningful; latest tells nobody what they are running.

04What stays outside the box

An image holds what is the same everywhere, and nothing that changes per machine or per person. Three things deliberately stay out:

  • Secrets. The API key is handed in at run time with --env-file. Baked into the image, everyone who pulls the image has your key.
  • Ports. The container listens on its own port 8000. You decide at run time which host port maps to it, so two containers can both use 8000 inside.
  • Data that must survive. When a container stops, everything written inside it is gone. Anything that must persist lives in a volume, a host folder mounted into the container. This is why the leaderboard vanishes on restart, and why Day 5 adds a database.

05The Oracle's Dockerfile, line by line

Save this as day01/oracle/Dockerfile. Every line is one step in the recipe and one layer in the image.

1FROM python:3.12-slim
2WORKDIR /app
3COPY --from=ghcr.io/astral-sh/uv:latest /uv /usr/local/bin/uv
4
5# dependencies first: cached until the lockfile changes
6COPY pyproject.toml uv.lock ./
7RUN uv sync --frozen --no-dev
8
9# then the code, which changes often
10COPY app ./app
11COPY static ./static
12COPY artifacts ./artifacts
13
14EXPOSE 8000
15CMD ["uv", "run", "--no-sync", "uvicorn", "app.main:app",
16     "--host", "0.0.0.0", "--port", "8000"]
  1. 1

    Start from an official image that already has Python 3.12 on a small Debian. You never install Python yourself.

  2. 2

    Work in /app inside the image. Every later path is relative to it.

  3. 3

    Copy the uv binary out of uv's own image. One file, no installer.

  4. 6–7

    Copy only the two dependency files, then install exactly the locked versions. --frozen refuses to resolve anything new: the image gets what your laptop had.

  5. 10–12

    Now copy the code and models. Editing a Python file only rebuilds from here down; the slow install above is reused.

  6. 14

    Document the port. A note for humans and tools; it opens nothing by itself.

  7. 15–16

    The command that runs when the container starts. Note 0.0.0.0: inside a container, localhost means "this container only". Bind to all interfaces or nothing outside can reach you. Everyone makes this mistake once.

06Build, run, look, ship

docker build -t oracle:day2 .
recipe → imageReads the Dockerfile in this folder, produces an image tagged oracle:day2.
docker run --rm -p 8000:8000 \
  --env-file .env oracle:day2
image → containerStarts one container, maps the port, hands in the key. --rm deletes it when it stops.
docker ps
docker logs -f NAME
docker stop NAME
lookWhat is running, what it is saying, and how to stop it.
docker tag oracle:day2 ghcr.io/YOU/oracle:day2
docker push ghcr.io/YOU/oracle:day2
shipName it for a registry and push. Any machine can now pull it.

-p 8000:8000 reads "host port : container port". The .env file is never copied into the image. List .env, .venv, and data/raw in .dockerignore so they are not even sent to the build.

07Several containers, one file

On Day 5 the agent, the models, and a database become separate containers. Docker Compose is one YAML file naming each of them; docker compose up starts them all and they reach each other by name. That is why the Oracle's tools read MODEL_API_URL from the environment instead of hard-coding localhost.

08Mistakes to make on purpose, once

  • Binding to 127.0.0.1 inside the container. The app runs; nothing can reach it.
  • Copying the whole folder before installing. Every code edit reinstalls every package.
  • Baking .env into the image. Run docker history on it and read your own key back.
  • Shipping :latest. Next week's "latest" is a different image and nobody can say which.
  • A 2 GB image because the base was python:3.12 not -slim, and the raw survey CSV came along for the ride.

The one sentence to remember: the image holds everything that is the same everywhere; the run command supplies everything that is not.
