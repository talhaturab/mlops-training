ECR and ECS Express Mode, in plain English

Running the same image without a server you manage.

01What we do today

On Day 1 you rented a Linux machine, installed Docker on it, copied the image to it, and started the container yourself. On Day 2 a pipeline did the copying and starting for you, but the machine was still yours: you created it, opened its ports, put the key on it, and you would have to patch it, resize it, and replace it when it fails.

Today we give the image to AWS and AWS runs it. We use two services. ECR stores the image inside AWS. ECS takes an image from ECR and runs it on machines AWS owns. ECS has a simplified form called Express Mode: you give it an image and a port, and it builds the load balancer, the HTTPS address, the logging and the scaling around it. We do not change a line of application code. The result is the same Oracle at a new URL, with no machine for us to manage.

You will also meet two services that every other AWS service depends on: IAM, which decides who may do what, and CloudWatch Logs, where the container's output goes. Both are explained below before we use them.

02The services, one at a time

Each service below is described the same way: what it is, what it does for us, what you configure, and how it is billed.

IAM Identity and Access Management

What it is
The permission system for the whole of AWS. Every action, in the console or from the command line, is a request that IAM checks against a policy before it runs. There is no "logged in as admin" state that bypasses it.
The words
A user is a person or a program with long-lived credentials. A role is a set of permissions that something assumes temporarily: you, when you sign in through the access portal; a service, when it needs to act on your behalf. A policy is a JSON document listing allowed and denied actions on specific resources. A service control policy is a policy applied by the organisation above the account; it is why some instance types are denied for us, and why App Runner is not available.
Why today
ECS needs two roles. The task execution role is what ECS uses to start our container: pull the image from ECR and write logs. The infrastructure role is what Express Mode uses to build the load balancer, its certificate and the scaling rules. Neither can use your login. The console offers to create both when you pick "Create new role"; you should still know they exist.
Billing
Free.

ECR Elastic Container Registry

What it is
A container registry that lives inside your AWS account, in one region. It does the same job as GitHub Container Registry: it stores images and their layers, and other machines pull from it. The difference is access control. Access to ECR is decided by IAM, so AWS services such as ECS can be given permission to read from it without any password.
The words
A repository holds the versions of one image, for example all tags of oracle. A repository is private by default. The full image address is ACCOUNT_ID.dkr.ecr.REGION.amazonaws.com/oracle:TAG.
What you configure
The repository name, and optionally a lifecycle rule that deletes old tags so storage does not grow forever.
How you log in
aws ecr get-login-password asks IAM for a token that is valid for 12 hours; you pipe it into docker login. No permanent registry password exists.
Billing
Storage per GB per month (a few cents for our image) and data transfer out of the region. Pulls by ECS in the same region are free.

ECS Elastic Container Service, in Express Mode, on Fargate

What it is
The AWS service that runs containers. Three words come with it. Fargate means AWS supplies the machines and you never see them. A task is one running copy of your container. Express Mode is a one-page form: image, port, size, and ECS creates everything else: a load balancer, a TLS certificate and an HTTPS address, a log group, scaling rules, and an alarm that undoes a bad deployment.
What it replaces
Everything you did by hand on Day 1 after docker build: choosing a machine, installing Docker, opening ports, starting the container with a restart policy, and getting HTTPS. When you give it a new image, it starts the new version next to the old one, checks its health, sends it a little traffic first, and only then moves everything over.
What you configure
The image address and tag. The port the app listens on (8000). CPU and memory per task (0.5 vCPU, 1 GB for us). Environment variables (our .env contents, typed into the console). A health check path (/health). The minimum and maximum number of tasks.
What you cannot do
Log in to the machine, because there is no machine you own. Attach a disk that survives restarts. Use an arm64 image: Express Mode runs x86 tasks, which is why we build for linux/amd64.
Billing
Per vCPU-hour and per GB-hour for every task, every second it exists, plus an hourly charge for the load balancer. See the cost section.

CloudWatch Logs where the output goes

What it is
The log storage service. Anything the container writes to standard output, which for us is uvicorn's request lines and Python tracebacks, is collected into a log group for the service, one log stream per running task.
Why today
On Day 1 you ran docker logs over SSH. There is no SSH now. The Logs tab on the service page, and the CloudWatch console, are the only ways to see what the app printed. Day 8 builds on this.
Billing
Per GB ingested and stored. Negligible at our volume.

04What happens to one request

It helps to follow a single chat message from the browser to the model and back, because several things now happen between the user and our code that used to not exist.

Two details are worth stating. First, the app never sees HTTPS; the load balancer handles the certificate and forwards plain HTTP, so the Dockerfile and the uvicorn command do not change. Second, because every task contains both the agent and the model endpoints, MODEL_API_URL stays http://localhost:8000. On Day 6, when the models become their own service, that variable changes and nothing else does.

05The steps

Region: Europe (London). Replace ACCOUNT_ID with the twelve-digit account number shown at the top right of the console. Budget 30 minutes, most of it waiting for the first deployment.

Step 1. Create the ECR repository (console)

  1. 1

    Open Elastic Container Registry. Click Create repository.

  2. 2

    Visibility Private. Name oracle-<yourname>. Leave the rest at defaults. Click Create.

  3. 3

    Open the repository and click View push commands. The four commands shown are the ones in Step 2, with your account number filled in.

Step 2. Push the image once by hand (your laptop)

aws ecr get-login-password --region eu-west-2 \
  | docker login --username AWS --password-stdin ACCOUNT_ID.dkr.ecr.eu-west-2.amazonaws.com

docker tag oracle:day1-amd64 \
  ACCOUNT_ID.dkr.ecr.eu-west-2.amazonaws.com/oracle-<yourname>:v1
docker push ACCOUNT_ID.dkr.ecr.eu-west-2.amazonaws.com/oracle-<yourname>:v1
  1. login

    The first command asks IAM for a 12-hour token and hands it to Docker. The user name is literally AWS. If this fails with an authorisation error, your command line is not signed in: run aws sso login first.

  2. tag

    A tag is a second name for the same image. The name has to start with the registry address so Docker knows where to push. We use v1, not latest, because ECS records exactly which image a deployment used, and a name that changes meaning makes that record useless.

  3. push

    Uploads the layers. Refresh the repository page: one image, tagged v1, about 300 MB. If the push says the repository does not exist, Step 1 was skipped or done in another region.

Step 3. Create the ECS Express service (console)

  1. 1

    Open Elastic Container Service. In the left menu click Express mode.

  2. 2

    Image URI: click Browse ECR images. Private repository is oracle-<yourname>, Select image by Image tag, tag v1.

  3. 3

    Task execution role: Create new role. Infrastructure role: Create new role. These are the two IAM roles from section 02. They are created when you click Create at the end.

  4. 4

    Open Additional configurations. Name: oracle-<yourname>. The name becomes part of the URL, so keep it short and lowercase.

  5. 5

    Container port: 8000. This is the single most common thing to get wrong. The default is 80; the app listens on 8000.

  6. 6

    Health check path: /health. The load balancer calls this before sending traffic to a new task and keeps calling it while the task runs.

  7. 7

    Environment variables: add each line of your .env as a key and value with Value type Environment variable: OPENROUTER_API_KEY, LLM_MODEL, LLM_BASE_URL, MODEL_API_URL = http://localhost:8000. Plain text for now; Day 4 moves the key to Secrets Manager and picks "Secret" here instead.

  8. 8

    CPU 0.5 vCPU, Memory 1 GB. Minimum number of tasks 1, Maximum number of tasks 2. The default maximum is 20; a bug that eats CPU would start 20 copies and bill you for them.

  9. 9

    Leave Customize networking configurations unticked, so the service uses the account's default network, and leave Logs at their defaults. Click Create. If the first attempt fails with "Unable to assume the service linked role", wait a few seconds and click Create again; the roles were still being made.

  10. 10

    Wait. The Resources tab shows a timeline: load balancer, certificate, target group, then the task starting and passing its health check. Five to ten minutes. The Application URL on the overview turns into a link when the service is ready.

Step 4. Use it

  1. URL

    Click the Application URL, an address like https://oracle-<yourname>.ecs.eu-west-2.on.aws. It is HTTPS. Chat with the Oracle.

  2. Logs

    Open the Logs tab. These are the container's output, the same lines you saw with docker logs. The Deployments tab records what ECS itself did.

  3. Update

    Change a line of the app, rebuild for amd64, tag and push to ECR as v2. Pushing alone changes nothing: ECS keeps running the image it was told to run. On the service page click Update service, browse to tag v2, click Update. ECS starts the new version next to the old one, checks /health, sends it 5% of traffic, watches for errors for three minutes, then moves all traffic over and stops the old task. About ten minutes, with the site up the whole time.

06Connecting the pipeline

Step 2's manual push is what the pipeline will do from now on. The Day 2 workflow gains one job that logs in to ECR and pushes the image there, tagged with the commit. The SSH deploy job is not needed for this target.

Two things stay manual today. The job needs AWS credentials, and for now they are an IAM user's access key and secret stored as GitHub secrets, the same way the SSH key was: a long-lived credential in a third party's vault, acceptable for a classroom and not for production. And the push does not deploy: someone still clicks Update service and picks the new tag. Day 4 fixes both. GitHub proves its identity to AWS per run with no stored key, and the deploy is a file in git that names the tag, so a merge is the deployment.

  push-to-ecr:
    needs: build-and-push
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          aws-access-key-id:     ${{ secrets.AWS_ACCESS_KEY_ID }}
          aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          aws-region: eu-west-2
      - uses: aws-actions/amazon-ecr-login@v2
        id: ecr
      - run: |
          src="ghcr.io/OWNER/oracle:${GITHUB_SHA::7}"
          dst="${{ steps.ecr.outputs.registry }}/oracle:${GITHUB_SHA::7}"
          docker pull "$src"
          docker tag "$src" "$dst"
          docker push "$dst"
  1. creds

    Exchanges the stored access key for a session on the runner. Everything after this line runs as that IAM user.

  2. login

    The same 12-hour token exchange you did by hand in Step 2, as an action.

  3. run

    Pulls the image the previous job built, gives it the ECR name with the commit as its tag, pushes it. The tag in ECR now tells you which commit it came from. The pipeline's own health check is not needed: ECS refuses to send traffic to a task that fails /health.

07EC2 versus ECS, item by item

ConcernEC2 (Days 1 and 2)ECS Express Mode (today)
Choosing and creating a machineYou, in the console, within the instance types allowedAWS. You choose CPU and memory per task only
Installing DockerYou, over SSHNot needed
Opening portsYou, in a security groupECS writes the security groups. Only the HTTPS endpoint is public
Getting the image onto the machinescp, or a registry pull over SSHECS pulls from ECR using the execution role
Starting and restarting the containerdocker run with a restart policyManaged. Failed tasks are replaced
HTTPSNot done. Plain HTTP on port 8000Included, with a certificate AWS renews
Handling more trafficBuy a bigger instance, by handMore tasks start automatically, up to the maximum you set
SecretsA file on the diskEnvironment variables held by the service; Secrets Manager on Day 4
Logsdocker logs over SSH; gone when the instance isCloudWatch Logs, kept after the task is gone
Deploying a new versionThe Day 2 SSH job: stop the old, start the newUpdate service: the new version runs next to the old, earns traffic, and a failure rolls back
Logging in to the machineSSHNot needed, and off by default
Persistent filesThe instance disk, until the instance is terminatedNone. Anything written inside a task is lost when the task stops
OS patchingYouAWS

You give up the last three rows to get the first ten. For the Oracle, none of the three matters: the app does not need a shell, it writes nothing it needs to keep, and the only state it has (chat memory, the leaderboard) was already lost on every restart. Day 4 moves that state into a database, which is the correct fix regardless of where the app runs.

So about $45 a month against $19 for the EC2 instance. Unlike App Runner, Fargate does not get cheaper when idle: a task costs the same whether it serves one request or a million. What the extra $26 buys is HTTPS, scaling, patching, replacement when the machine fails, and a deployment that cannot take the site down. Whether that is worth it depends on how much of your time those things take. For a whole class in one account, the load balancer is shared, so each extra student costs about $27.

09Mistakes to make on purpose, once

  • Port left at the default 80. Health checks fail forever, the deployment never completes, and the Deployments tab says the target is unhealthy.
  • Health check path left at /. It works, because / serves the page, but a broken model load would go unnoticed. Use /health.
  • No environment variables. The service starts, the page loads, and chat answers "The Oracle is asleep".
  • Pushing the arm64 image. The task exits immediately with exec format error and ECS starts another, over and over.
  • Repository in one region, service in another. The image browser is empty. Both must be in London.
  • Pushing a new image with the same tag and expecting a redeploy. ECS runs what it was told to run until you click Update service. Use a new tag each time.

The one sentence to remember: ECS Express Mode takes an image and a port and does everything you did by hand on Day 1 after docker build; the price is that you cannot log in to the machine, because there is no machine.
