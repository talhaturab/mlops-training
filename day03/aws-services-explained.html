01How they fit around the Oracle

AWS is a catalogue of separate services. Each does one job and has its own console page, its own prices, and its own permissions. We use eight of them over the course. This is where each one sits.

02Each service, one at a time

IAM

Who is allowed to do what.

Every action on AWS is a request, and IAM answers yes or no by reading a policy attached to the identity making the request. People sign in and get a role; services that act for you also get a role.

Nothing bypasses it. If something fails with "not authorized", the answer is a policy, not a bug in the service.

Every day · Day 4 in depth

EC2

A computer you rent by the hour.

You choose its size and operating system. Everything else, from installing Docker to opening ports, is yours to do. The security group is its firewall: a list of ports and who may reach them.

It is the least managed service here, which is why we used it first.

Days 1 and 2

ECR

A place to store container images inside AWS.

A repository holds the versions of one image, each with a tag. You push to it from a laptop or a pipeline; servers and App Runner pull from it.

Same idea as GitHub Container Registry. The difference is that access is decided by IAM, so AWS services can pull without a password.

Day 3

App Runner

Runs a container image as a website, no server to manage.

You give it an image and a port. It starts copies of the container, puts a load balancer in front, issues an HTTPS certificate, and gives you a URL. When a new image appears in ECR, it deploys it after a health check.

You cannot log in to the machine, because you are not given one.

Day 3

CloudWatch Logs

Where printed output goes when there is no terminal.

Anything the container writes to standard output is collected into a log group. You read and search it in the console, during and after the container's life.

On Day 1 this was docker logs over SSH. Now there is no SSH.

Day 3 · Day 8 in depth

Secrets Manager

A locked store for keys and passwords.

You put the value in once. The running app asks for it by name, using its IAM role, and gets it in memory. Access is logged and the value can be rotated without redeploying.

This removes the .env file from every machine.

Day 4

S3

Files of any size, stored by name.

A bucket holds objects: model artifacts, datasets, exported images, anything. Training jobs write to it, the app reads from it at startup, and the pipeline can do both.

It replaces the model files we committed to git on Day 1.

Day 6

RDS

A database AWS runs for you.

A managed Postgres. Every copy of the app reads and writes the same rows, so chat sessions and the leaderboard survive restarts and are shared between copies.

Backups, patching, and failover are AWS's job. Writing the tables is ours.

Day 5

The one sentence to remember: each AWS service does one job; the console, the price, and the permissions are separate for each one, and IAM sits in front of all of them.
