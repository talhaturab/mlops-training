ECR and App Runner, in plain English

Running the same image without a server you manage.

01What we do today

On Day 1 you rented a Linux machine, installed Docker on it, copied the image to it, and started the container yourself. On Day 2 a pipeline did the copying and starting for you, but the machine was still yours: you created it, opened its ports, put the key on it, and you would have to patch it, resize it, and replace it when it fails.

Today we give the image to AWS and AWS runs it. We use two services. ECR stores the image inside AWS. App Runner takes an image from ECR and runs it as a web service with an HTTPS address. We do not change a line of application code. The result is the same Oracle at a new URL, with no machine for us to manage.

You will also meet two services that every other AWS service depends on: IAM, which decides who may do what, and CloudWatch Logs, where the container's output goes. Both are explained below before we use them.

02The services, one at a time

Each service below is described the same way: what it is, what it does for us, what you configure, and how it is billed.

IAM Identity and Access Management

What it is
The permission system for the whole of AWS. Every action, in the console or from the command line, is a request that IAM checks against a policy before it runs. There is no "logged in as admin" state that bypasses it.
The words
A user is a person or a program with long-lived credentials. A role is a set of permissions that something assumes temporarily: you, when you sign in through the access portal; a service, when it needs to act on your behalf. A policy is a JSON document listing allowed and denied actions on specific resources. A service control policy is a policy applied by the organisation above the account; it is why some instance types are denied for us.
Why today
App Runner has to pull the image from ECR. It cannot use your login, so it assumes a role that permits only ecr:GetDownloadUrlForLayer, ecr:BatchGetImage, and a few related actions. The console creates that role for you when you tick a box; you should still know it exists.
Billing
Free.

ECR Elastic Container Registry

What it is
A container registry that lives inside your AWS account, in one region. It does the same job as GitHub Container Registry: it stores images and their layers, and other machines pull from it. The difference is access control. Access to ECR is decided by IAM, so AWS services such as App Runner can be given permission to read from it without any password.
The words
A repository holds the versions of one image, for example all tags of oracle. A repository is private by default. The full image address is ACCOUNT_ID.dkr.ecr.REGION.amazonaws.com/oracle:TAG.
What you configure
The repository name, and optionally a lifecycle rule that deletes old tags so storage does not grow forever.
How you log in
aws ecr get-login-password asks IAM for a token that is valid for 12 hours; you pipe it into docker login. No permanent registry password exists.
Billing
Storage per GB per month (a few cents for our image) and data transfer out of the region. Pulls by App Runner in the same region are free.

App Runner a managed container web service

What it is
A service that runs a container image as a web application. You give it an image and a port. It starts one or more copies of the container on machines AWS owns, puts a load balancer in front of them, issues a TLS certificate, and gives you an HTTPS address. When traffic rises it starts more copies; when traffic stops it keeps one copy provisioned and charges you less for it.
What it replaces
Everything you did by hand on Day 1 after docker build: choosing a machine, installing Docker, opening ports, starting the container with a restart policy, and getting HTTPS. It also replaces the deploy job from Day 2: when a new image appears in ECR under the tag it watches, it deploys it, checks health, and only then moves traffic.
What you configure
The image address and tag. The port the app listens on (8000). CPU and memory per copy (1 vCPU, 2 GB for us). Environment variables (our .env contents, typed into the console). A health check path (/health). Whether to deploy automatically when the tag changes.
What you cannot do
Log in to the machine. Attach a disk that survives restarts. Run anything that is not an HTTP service on one port. Use an arm64 image; App Runner runs x86 only, which is why we build for linux/amd64.
Billing
Per vCPU-hour and per GB-hour while a copy is handling requests. When idle, only the memory is charged, at a lower rate. See the cost section.

CloudWatch Logs where the output goes

What it is
The log storage service. Anything the container writes to standard output, which for us is uvicorn's request lines and Python tracebacks, is collected into a log group for the service, one log stream per running copy.
Why today
On Day 1 you ran docker logs over SSH. There is no SSH now. The Logs tab in App Runner, and the CloudWatch console, are the only ways to see what the app printed. Day 8 builds on this.
Billing
Per GB ingested and stored. Negligible at our volume.

04What happens to one request

It helps to follow a single chat message from the browser to the model and back, because several things now happen between the user and our code that used to not exist.

Two details are worth stating. First, the app never sees HTTPS; App Runner handles the certificate and forwards plain HTTP, so the Dockerfile and the uvicorn command do not change. Second, because every copy contains both the agent and the model endpoints, MODEL_API_URL stays http://localhost:8000. On Day 5, when the models become their own service, that variable changes and nothing else does.

05The steps

Region: Europe (London). Replace ACCOUNT_ID with the twelve-digit account number shown at the top right of the console. Budget 25 minutes, most of it waiting for the first deployment.

Step 1. Create the ECR repository (console)

  1. 1

    Open Elastic Container Registry. Click Create repository.

  2. 2

    Visibility Private. Name oracle-<yourname>. Leave the rest at defaults. Click Create.

  3. 3

    Open the repository and click View push commands. The four commands shown are the ones in Step 2, with your account number filled in.

Step 2. Push the image once by hand (your laptop)

aws ecr get-login-password --region eu-west-2 \
  | docker login --username AWS --password-stdin ACCOUNT_ID.dkr.ecr.eu-west-2.amazonaws.com

docker tag oracle:day1-amd64 \
  ACCOUNT_ID.dkr.ecr.eu-west-2.amazonaws.com/oracle-<yourname>:latest
docker push ACCOUNT_ID.dkr.ecr.eu-west-2.amazonaws.com/oracle-<yourname>:latest
  1. login

    The first command asks IAM for a 12-hour token and hands it to Docker. The user name is literally AWS. If this fails with an authorisation error, your command line is not signed in: run aws sso login first.

  2. tag

    A tag is a second name for the same image. The name has to start with the registry address so Docker knows where to push.

  3. push

    Uploads the layers. Refresh the repository page: one image, tagged latest, about 300 MB. Note the x86 image is required; App Runner does not run arm64.

Step 3. Create the App Runner service (console)

  1. 1

    Open App Runner. Click Create service.

  2. 2

    Source: Container registry, Amazon ECR. Browse to your repository and pick the latest tag.

  3. 3

    Deployment trigger: Automatic. This is what makes a later docker push of the same tag redeploy the service.

  4. 4

    ECR access role: Create new service role. This is the IAM role that lets App Runner read from your repository. Click Next.

  5. 5

    Service name: oracle-<yourname>. CPU 1 vCPU, Memory 2 GB.

  6. 6

    Environment variables: add each line of your .env as a name and value: OPENROUTER_API_KEY, LLM_MODEL, LLM_BASE_URL, MODEL_API_URL = http://localhost:8000. Choose "Plain text" for now; Day 4 changes this to a Secrets Manager reference.

  7. 7

    Port: 8000. This is the single most common thing to get wrong. The app listens on 8000; App Runner forwards to whatever you type here.

  8. 8

    Health check: Protocol HTTP, Path /health. App Runner calls this before sending traffic to a new copy and keeps calling it while the copy runs. Leave the intervals at their defaults.

  9. 9

    Leave Auto scaling, Networking, and Security at their defaults. Click Next, review, Create & deploy.

  10. 10

    Wait. The status goes from Operation in progress to Running in five to ten minutes. The Event log on the service page shows each stage: pulling the image, starting a copy, health check passed, routing traffic.

Step 4. Use it

  1. URL

    Click the Default domain, an address ending in .awsapprunner.com. It is HTTPS. Chat with the Oracle.

  2. Logs

    Open the Logs tab. Application logs are the container's output, the same lines you saw with docker logs. Deployment logs record what App Runner itself did.

  3. Update

    Change a line of the app, rebuild for amd64, tag and push to ECR as latest again. Within a minute the service page shows a new deployment; a few minutes later the URL serves the new version. No SSH, no commands on a server.

06Connecting the pipeline

Step 4's manual push is what the pipeline will do from now on. The Day 2 workflow gains one job that logs in to ECR and pushes the image there, and the SSH deploy job is no longer needed for this target: App Runner redeploys on its own when the latest tag changes.

The job needs AWS credentials. For today they are an IAM user's access key and secret, stored as GitHub secrets, the same way the SSH key was. That is a long-lived credential sitting in a third party's vault, which is acceptable for a classroom and not for production. Day 4 replaces it with an OpenID Connect trust, where GitHub proves its identity to AWS per run and no stored key exists.

  push-to-ecr:
    needs: build-and-push
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          aws-access-key-id:     ${{ secrets.AWS_ACCESS_KEY_ID }}
          aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          aws-region: eu-west-2
      - uses: aws-actions/amazon-ecr-login@v2
        id: ecr
      - run: |
          src="ghcr.io/OWNER/oracle:${GITHUB_SHA::7}"
          dst="${{ steps.ecr.outputs.registry }}/oracle:latest"
          docker pull "$src"
          docker tag "$src" "$dst"
          docker push "$dst"
  1. creds

    Exchanges the stored access key for a session on the runner. Everything after this line runs as that IAM user.

  2. login

    The same 12-hour token exchange you did by hand in Step 2, as an action.

  3. run

    Pulls the image the previous job built, gives it the ECR name, pushes it. App Runner notices the new latest and deploys. The pipeline's own health check is no longer needed because App Runner refuses to route traffic to a copy that fails /health.

07EC2 versus App Runner, item by item

ConcernEC2 (Days 1 and 2)App Runner (today)
Choosing and creating a machineYou, in the console, within the instance types allowedAWS. You choose CPU and memory per copy only
Installing DockerYou, over SSHNot needed
Opening portsYou, in a security groupNot needed. Only the HTTPS endpoint is public
Getting the image onto the machinescp, or a registry pull over SSHApp Runner pulls from ECR using an IAM role
Starting and restarting the containerdocker run with a restart policyManaged. Failed copies are replaced
HTTPSNot done. Plain HTTP on port 8000Included, with a certificate AWS renews
Handling more trafficBuy a bigger instance, by handMore copies start automatically, up to a limit you set
SecretsA file on the diskEnvironment variables held by the service; Secrets Manager on Day 4
Logsdocker logs over SSH; gone when the instance isCloudWatch Logs, kept after the copy is gone
Deploying a new versionThe Day 2 SSH jobPush a new image to ECR; App Runner deploys with a health check
Logging in to the machineSSHNot possible
Persistent filesThe instance disk, until the instance is terminatedNone. Anything written inside a copy is lost when the copy stops
OS patchingYouAWS

You give up the last three rows to get the first ten. For the Oracle, none of the three matters: the app does not need a shell, it writes nothing it needs to keep, and the only state it has (chat memory, the leaderboard) was already lost on every restart. Day 5 moves that state into a database, which is the correct fix regardless of where the app runs.

Approximate prices for London at the time of writing. Check the pricing pages before quoting these to anyone; they change.

ItemRatePer month, running 24 hours a day
EC2 t2.smallabout $0.026 per hourabout $19, plus a few dollars for the disk
App Runner, 1 vCPU / 2 GB, handling requestsabout $0.064 per vCPU-hour plus $0.007 per GB-hourabout $57 if busy every minute of the month
App Runner, same size, idlememory only, about $0.007 per GB-hourabout $10 if idle the whole month
ECR storageabout $0.10 per GB-monthunder $1 for a handful of image versions

A classroom app that is used a few hours a day sits near the idle figure. The comparison people usually make, EC2 at $19 versus App Runner at $57, assumes the App Runner service is busy around the clock, which is rarely true. It also ignores that the EC2 figure buys no HTTPS, no scaling, no patching, and no replacement when the machine fails. Whether the trade is worth it depends on how much of your time those things take.

09Mistakes to make on purpose, once

  • Port left at the default. Health checks fail forever, the service never reaches Running, and the event log says the check timed out.
  • Health check path left at /. It works, because / serves the page, but a broken model load would go unnoticed. Use /health.
  • No environment variables. The service starts, the page loads, and chat answers "The Oracle is asleep".
  • Pushing the arm64 image. The copy exits immediately with exec format error and App Runner retries until it gives up.
  • Repository in one region, service in another. The image browser in App Runner is empty. Both must be in London.
  • Deployment trigger set to Manual, then wondering why a push to ECR changed nothing.

The one sentence to remember: App Runner takes an image and a port and does everything you did by hand on Day 1 after docker build; the price is that you cannot log in to the machine, because there is no machine.
