01The goal

On Day 2 a merge to main built an image and used an SSH key to log in to one EC2 server and run it. Today the same merge builds an image, tells CloudFormation which image the ECS service should run, and CloudFormation makes it so. Nothing is logged in to, and nothing is stored that could leak.

02What gets built

03Why two stacks

The pipeline cannot create the role it needs to log in, and it cannot push an image to a repository that does not exist yet. So those two things are made first, by hand, once. Everything else is made by the pipeline.

04How GitHub gets into AWS without a password

On Day 2 we pasted a private key into GitHub secrets. If it leaks, whoever has it can log in to the server until we notice. Today there is nothing to paste. GitHub signs a short statement about the running job, AWS checks the signature and the statement, and hands back credentials that expire in one hour.

The condition lives in the base stack. These are the lines that matter:

assumed_by=iam.WebIdentityPrincipal(
    provider.oidc_provider_arn,
    conditions={
        "StringEquals": {"token.actions.githubusercontent.com:aud": "sts.amazonaws.com"},
        "StringLike": {
            "token.actions.githubusercontent.com:sub": [
                "repo:talhaturab/mlops-training:ref:refs/heads/main",
                "repo:talhaturab@*/mlops-training@*:ref:refs/heads/main",
            ]
        },
    },
)

Two spellings of the same repository. Repositories created since 2025 get an "immutable subject": GitHub puts numeric ids after the owner and the name, so renaming the repository cannot break or hijack the trust. Older repositories use the plain form. Check which yours uses with gh api repos/OWNER/NAME/actions/oidc/customization/sub.

What the role may do. Push to the one repository, and switch into the roles that cdk bootstrap created. CDK never deploys as the GitHub role directly. It hands the template to CloudFormation, which runs as a bootstrap role. So the GitHub role's own permissions stay short.

05The pipeline

File: .github/workflows/oracle-aws.yml. Three jobs, same shape as Day 2. The test job is unchanged. The other two are new.

The deploy step, from the workflow file:

- name: cdk deploy
  run: >
    cdk deploy OracleAppStack
    -c image_tag=${{ needs.build-and-push.outputs.image_tag }}
    --require-approval never
    --outputs-file outputs.json
  • -c image_tag=… sets a context value. The stack reads it and puts it in the ECS service definition.
  • --require-approval never: a person is not there to press y. The diff step just before prints what will change, for the log.
  • --outputs-file writes the stack outputs, including the service URL, so the last step can check the live site.

06What happens on merge

07The database and the network

A database needs a private network, and so do the containers. This is the smallest one that works, and the stack builds all of it in about twelve lines.

VPC
Your own private network inside AWS, with an address range you choose. Nothing in it is reachable from outside unless you add a route and a firewall rule.
subnet
A slice of the VPC in one availability zone. Public ones have a route to the internet gateway. Isolated ones have no route out.
security group
A firewall attached to a resource. The rule we add: port 5432, from the tasks' group. Rules can name other groups, so no IP addresses appear.
load balancer
The public front door. It holds the HTTPS certificate, checks /health on every task, and spreads requests across them. ECS creates and owns it; up to 25 Express services share one.

In the app, the store chooses Postgres when it has a database URL and stays in memory otherwise. Two tables: a counter and the leaderboard. Every copy of the app reads the same rows, and a redeploy no longer resets the numbers.

08Where the secrets are

Two secrets, two different origins, one delivery path. Neither appears in git, in the pipeline logs, in the template, or in the console.

secrets=[
    ecs.CfnExpressGatewayService.SecretProperty(
        name="DB_PASSWORD", value_from=f"{db.secret.secret_arn}:password::"
    ),
    ecs.CfnExpressGatewayService.SecretProperty(
        name="OPENROUTER_API_KEY", value_from=openrouter.secret_arn
    ),
],

:password:: after the ARN means "the password field of that JSON secret". The OpenRouter secret is a plain string, so its ARN is enough.

09One-time setup, in order

Six steps from a laptop. After them, nobody runs a deploy by hand again.

  1. 1

    Sign in. aws sso login --profile talhasandbox. Everything below uses this profile.

  2. 2

    Bootstrap the account. npx aws-cdk bootstrap aws://824992912214/eu-west-2 --profile talhasandbox. Creates the bucket and the cdk- roles. Once per account and region.

  3. 3

    Deploy the base stack. npx aws-cdk deploy OracleBaseStack --profile talhasandbox from day04/infra. It prints DeployRoleArn.

  4. 4

    Tell GitHub the role. gh variable set AWS_DEPLOY_ROLE_ARN --body arn:aws:iam::824992912214:role/oracle-github-deploy. A variable, not a secret: the ARN is not sensitive, and the trust policy is what protects it.

  5. 5

    Store the OpenRouter key. aws secretsmanager create-secret --name oracle/openrouter --secret-string sk-or-… --region eu-west-2 --profile talhasandbox.

  6. 6

    Merge to main, or run the oracle-aws workflow from the Actions tab. The first run creates the network, the database and the service and takes about twenty minutes: RDS, then the load balancer and its certificate.

10Going back to an earlier version

Every image in ECR is tagged with its commit. Two ways to run an older one:

  • Revert the commit and merge. The pipeline builds and deploys the reverted code. Git history shows what happened and why. This is the normal way.
  • Re-run an older workflow run. Open the run for the commit you want in the Actions tab and press "Re-run all jobs". It deploys that commit's tag again. Faster, and nothing in git records it.

Either way it is a normal deploy: the old version keeps serving until the new one passes its health check.

12Mistakes to expect

  • "Not authorized to perform sts:AssumeRoleWithWebIdentity". The trust condition did not match. Check the repository name in cdk.json, that the workflow ran on main, not on a branch, and whether GitHub gives your repository the immutable subject with numeric ids (section 04).
  • "OIDC provider already exists". An account can have one provider for GitHub. This account already had one from another project, so the base stack imports it with OpenIdConnectProvider.from_open_id_connect_provider_arn instead of creating it.
  • The first deploy fails on the service. ECS cannot start an image that is not in ECR yet. The pipeline pushes before it deploys; a manual first deploy needs a pushed image with the tag you pass.
  • Secret not found: oracle/openrouter. Step 5 was skipped, or done in another region. The stack refers to the secret by name and expects it in eu-west-2.
  • Two pipelines deploy the same merge. The Day 2 workflow still runs on the same paths and still updates the EC2 server. Disable one when you no longer teach with it.
  • The app cannot reach the database. Check the security group rule exists and that the service was given our task security group. ECS adds its own groups; ours is the one the database trusts.
  • Old AWS CLI. Express Mode is new. If aws ecs create-express-gateway-service is "invalid choice", update the CLI. CDK does not need it; it talks to CloudFormation.

The one sentence to remember: the pipeline pushes an image tagged with the commit, tells CloudFormation that tag, and CloudFormation and ECS do the deployment, with a one-hour token instead of a key and a rollback instead of an outage.
