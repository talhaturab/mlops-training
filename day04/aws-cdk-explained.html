AWS CDK: infrastructure as code

Yesterday you clicked. Today you write the same thing down and let AWS do the clicking.

01What CDK is

CDK is a Python library and a command-line tool. You describe AWS resources in Python. The tool turns that into a CloudFormation template, and CloudFormation creates the resources. You never write the template by hand.

02Why not keep using the console

The console works for one person doing something once. It fails for a team doing the same thing many times, because clicks leave no record.

03The words

CloudFormation
The AWS service that reads a template and creates the resources in it. It records what it created as a stack and can update or delete the whole stack later.
template
A JSON or YAML file listing resources and their settings. CDK generates it. You almost never read it, and you never edit it.
stack
One CloudFormation unit: a template plus the live resources it created. CDK: one Python class. Deploy, diff and destroy work on a whole stack.
construct
A Python class that stands for one or more AWS resources. ecr.Repository is a construct. A stack is made of constructs.
app
The program that holds your stacks. app.py creates an App, adds stacks to it, and calls synth().
synth
Short for synthesize: run the Python and write the template to a folder called cdk.out. Nothing touches AWS.
bootstrap
A one-time setup per account and region. It creates an S3 bucket and a few IAM roles that cdk deploy needs.
asset
A local file CDK must upload before deploying, for example a Docker image or a Lambda zip. Assets go to the bootstrap bucket or ECR.

04How the code is organised

Three levels of nesting: an app holds stacks, a stack holds constructs, a construct becomes one or more resources.

Two files matter: app.py, which you rarely touch, and the stack file, where all the work happens.

06The service, as code

This is a whole stack file. It runs the Oracle image from ECR on ECS Express Mode, which is Fargate plus a load balancer plus an HTTPS URL, and prints the URL.

  1. 1–3

    Imports. Stack and CfnOutput are core. Each AWS service has its own module inside aws_cdk: here ECR, ECS and IAM.

  2. 6–8

    A stack is a class. scope is the app it belongs to, id is its name. Every construct takes these same two arguments first.

  3. 10

    Refers to the repository you made on Day 3 instead of creating a new one. ECS needs an image to exist when the service is created, and that repository already has one.

  4. 12–23

    Two roles ECS needs. The execution role is what ECS uses to start a container: pull the image, write logs. The infrastructure role is what ECS Express uses to build the load balancer, the certificate and the scaling around it. Each gets an AWS-written policy; you only say who may use the role.

  5. 25–35

    The service. Cfn at the front means L1: every property has the same name as in the CloudFormation docs, and nothing is filled in for you. Image, port, size, health check path. No network is given, so ECS uses the account's default VPC; the real Day 4 stack gives its own.

  6. 37

    An output is a value CloudFormation prints after deploy. Here it is the HTTPS URL that ECS gives the service, so you do not have to look for it in the console.

What you did not write. The cluster, the task definition, the load balancer and its listener, the HTTPS certificate, the security groups, the log group, auto scaling and the rollback alarm. ECS Express creates all of them from this one resource at deploy time. They are real resources in your account, but they are not in the template. Run cdk synth and look: the template has three resources.

applyUploads the template, waits for CloudFormation, prints the outputs. First run takes about 10 minutes: most of it is ECS building the load balancer and its certificate.

clean upDeletes every resource the stack created, in reverse order. The imported ECR repository is not deleted.

08What happens during deploy

CloudFormation works out the order from the dependencies in the template, creates resources one by one, and reports each step as an event. If any step fails, it undoes the ones before it.

09Changing something

To change the service, change the code and deploy again. CloudFormation compares the new template with the old one and touches only what differs.

The diff output uses three markers:

[+] something will be created
[-] something will be deleted
[~] something will be changed in place

Some changes replace the resource. Renaming a repository or changing a database engine cannot be done in place, so CloudFormation creates a new one and deletes the old one. The diff says requires replacement when this will happen. Read for it before you press y.

10What bootstrap made

Deploy needs somewhere to upload the template and a role to act as. Bootstrap creates those once. You will see them in the console as a stack called CDKToolkit.

11Mistakes to expect

  • Editing in the console after deploying with CDK. The next deploy puts it back to what the code says. Change the code instead.
  • Expired SSO session. cdk deploy fails with a token error. Run aws sso login --profile talhasandbox and try again.
  • Wrong region. The stack goes to the region in your profile or in app.py. Check the CloudFormation console in London, not the default region.
  • Creating the ECR repository and the service in one stack, with no image pushed yet. ECS cannot start the task, the health check never passes, and the whole stack rolls back. Push the image first, or import the repository as in the example.
  • Committing cdk.out. It is generated. Add it to .gitignore; cdk init already does this.
  • Reading a "not authorized" error as a CDK bug. It is IAM. The identity you deploy with, or the role CloudFormation uses, is missing a permission. Bootstrap needs permission to create S3 buckets and IAM roles.

The one sentence to remember: CDK turns Python into a CloudFormation template, CloudFormation turns the template into resources, and the code in git is the record of what exists.
